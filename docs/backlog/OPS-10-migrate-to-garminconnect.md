# OPS-10 · Виконати міграцію Garmin-auth на python-garminconnect

**Тип:** операційна стійкість · **Оцінка:** M · **Пріоритет:** P1 —
**проактивна** міграція (робимо наперед, поки garth ще працює, а не за фактом
поломки) · **Залежності:** OPS-01 (розвідка + план — зроблено), PERF-05
(rate limit живе в тому самому шарі клієнта — вже є), ST-06 (MFA-міст —
адаптується тут)

## Проблема

`garth==0.4.47` (пінований) досі логіниться повз Cloudflare, але бібліотека
офіційно deprecated з 2026-03-28 — обхід тримається лише на старому mobile-флоу
0.4.x і може зламатися будь-коли (ANALYSIS.md §0, OPS-01). OPS-01 закрив
**підготовку**: розвідка `python-garminconnect` 0.3.6 (curl_cffi) проти живого
акаунта з IP проду — **0 FAIL** на логіні+MFA, token resume і всіх наших
read-endpoint-ах; план міграції розписано покроково. Свідомо лишили тригер
«мігрувати за фактом поломки».

Це рішення переглянуто: замість чекати на `GARMIN AUTH FAIL` у проді (де свап
провайдера — це вже пожежа під тиском), робимо **контрольовану** міграцію зараз,
поки garth як робочий відкат за один `pip install -e .`.

## Поточний стан коду (звірено 2026-07-26)

- Реальний per-user шлях **захардкоджений на garth**: `providers.build_user_provider`
  → `_UserGarthProvider` (`from garth import Client`). Вибору провайдера для
  per-user рантайму немає.
- `_GConnProvider` існує, але підключений лише до legacy single-user
  `_default_provider()` під `GARMIN_PROVIDER=gconn`, і позначений
  «UNTESTED … Do not rely on it in production». Це **не** цільовий клас міграції —
  цільовий це новий `_UserGConnProvider` (аналог `_UserGarthProvider`).
- Пін у `pyproject.toml`: `garth==0.4.47`, `garminconnect` (без піна, тягне 0.2.8
  через старий garth). Дев-venv на маку — Python 3.9; **Pi — Python 3.13.5**;
  garminconnect 0.3.6 вимагає **≥ 3.12**.

## Acceptance criteria

- [ ] **Залежності**: у `pyproject.toml` розпінити на `garminconnect>=0.3.6`,
      прибрати `garth==0.4.47`. Апгрейд дев-venv на маку до ≥ 3.12 (Pi вже 3.13.5).
      Звірити, що для `curl_cffi` є aarch64-wheel (pip не має компілювати на Pi).
- [ ] **Провайдер**: додати `_UserGConnProvider` у `app/garmin/providers.py` —
      аналог `_UserGarthProvider`: ізольований стан на юзера, `connectapi(path,
      **kwargs)` того самого інтерфейсу (`client.py` НЕ чіпається), resume зі
      збереженого в БД токен-блоба, `new_token` після свіжого логіну.
      `build_user_provider` перемикається на нього.
- [ ] **Формат токена**: звірити 0.3.6 token-store (`api.client.dump`/`load`,
      garth-стиль — прогін 2 OPS-01) зі збереженими в БД garth-блобами. Якщо не
      бінарно-сумісні — написати одноразову конвертацію АБО стратегію
      «стара сесія не резюмиться → тихий свіжий логін» (OAuth1 юзера 1 живий до
      ≈2027-07, тож re-login один раз не критичний).
- [ ] **MFA-міст** (`app/garmin/mfa.py`): у `_run`-потоці замінити
      `client.login(email, password, prompt_mfa=...)` на конструктор/`login()`
      0.3.6 з тим самим parked-callback `prompt_mfa`. Веб-флоу `/settings`,
      `MFARequired`, 409-handler і морнінг-джоба — **без змін**. (Якщо 0.3.6 дає
      `return_on_mfa`/`resume_login` — міст можна спростити без фонового потоку;
      але це окремий крок, спершу мінімальний діф.)
- [ ] **Token refresh**: перевірити автооновлення DI-токенів новою бібліотекою —
      «раз на рік логін» може зникнути. Якщо оновлений стан треба реперсистити —
      розширити `runtime.user_runtime` (він уже вміє зберігати `new_token`).
- [ ] **Write-раундтріп** (`--write-test`, свідомо відкладений в OPS-01): один раз
      прогнати `scripts/ops01_recon_gconn.py --write-test` на Pi — create →
      schedule → delete workout — перед свапом провайдера. `push-plan` / `plan_sync`
      пишуть у календар, тож цю гілку треба закрити до релізу.
- [ ] **Rate limit (PERF-05)**: підтвердити, що `client._RateLimiter` + 429-backoff
      у `client._api` працюють над новим движком (curl_cffi) без змін — після
      Cloudflare-ери агресивні патерни → ризик бана акаунта, не лише 429.
- [ ] **`_GConnProvider` (legacy)**: або видалити старий untested клас, або
      переписати під 0.3.6 API (у 0.2.x токени/профіль жили на `api.garth`, у 0.3.6
      немає — `AttributeError` з прогону 1). Не лишати мертвий клас, що бреше.
- [ ] **Верифікація**: `pytest` зелений (провайдер мокається — тести не залежать
      від бібліотеки) + `ruff` + один живий цикл на Pi: `/report` → morning job →
      `push-plan --dry-run` → реальний MFA-конект через `/settings`.

## Ризики / підводні камені

- Обхід Cloudflare — гонка озброєнь: 0.3.6 теж може зламатися. Прийнято свідомо
  (постійний податок неофіційного API, ANALYSIS.md §2.4).
- **Відкат**: пін `garth==0.4.47` лишається в git-історії — стан «до» за один
  `pip install -e .`. Не видаляти робочий garth-шлях, поки нове не відкатано в
  проді хоча б цикл.
- MFA-конект досяжний **тільки у веб-процесі** (`app.garmin.mfa`) — тестувати
  через реальний `/settings`, не з CLI.
- **Cost-safety**: живий цикл `/report`/morning робить справжній Claude-виклик —
  запускати лише з дозволу (CLAUDE.md §Cost safety), решту ганяти на мок-suite.
