# OPS-10 · Виконати міграцію Garmin-auth на python-garminconnect

**Тип:** операційна стійкість · **Оцінка:** M · **Пріоритет:** P1 —
**проактивна** міграція (робимо наперед, поки garth ще працює, а не за фактом
поломки) · **Залежності:** OPS-01 (розвідка + план — зроблено), PERF-05
(rate limit живе в тому самому шарі клієнта — вже є), ST-06 (MFA-міст —
адаптується тут)

## Проблема

`garth==0.4.47` (пінований) досі логіниться повз Cloudflare, але бібліотека
офіційно deprecated з 2026-03-28 — обхід тримається лише на старому mobile-флоу
0.4.x і може зламатися будь-коли (ANALYSIS.md §0, OPS-01). OPS-01 закрив
**підготовку**: розвідка `python-garminconnect` 0.3.6 (curl_cffi) проти живого
акаунта з IP проду — **0 FAIL** на логіні+MFA, token resume і всіх наших
read-endpoint-ах; план міграції розписано покроково. Свідомо лишили тригер
«мігрувати за фактом поломки».

Це рішення переглянуто: замість чекати на `GARMIN AUTH FAIL` у проді (де свап
провайдера — це вже пожежа під тиском), робимо **контрольовану** міграцію зараз,
поки garth як робочий відкат за один `pip install -e .`.

## Стан коду ДО міграції (звірено 2026-07-26) — знімок «як було»

- Реальний per-user шлях **захардкоджений на garth**: `providers.build_user_provider`
  → `_UserGarthProvider` (`from garth import Client`). Вибору провайдера для
  per-user рантайму немає.
- `_GConnProvider` існує, але підключений лише до legacy single-user
  `_default_provider()` під `GARMIN_PROVIDER=gconn`, і позначений
  «UNTESTED … Do not rely on it in production». Це **не** цільовий клас міграції —
  цільовий це новий `_UserGConnProvider` (аналог `_UserGarthProvider`).
- Пін у `pyproject.toml`: `garth==0.4.47`, `garminconnect` (без піна, тягне 0.2.8
  через старий garth). Дев-venv на маку — Python 3.9; **Pi — Python 3.13.5**;
  garminconnect 0.3.6 вимагає **≥ 3.12**.

## Acceptance criteria

- [x] **Залежності**: у `pyproject.toml` розпінити на `garminconnect>=0.3.6`,
      прибрати `garth==0.4.47`. Апгрейд дев-venv на маку до ≥ 3.12 (Pi вже 3.13.5).
      Звірити, що для `curl_cffi` є aarch64-wheel (pip не має компілювати на Pi).
      → `garminconnect>=0.3.6` у базі, garth переїхав у **extra `garth`** (відкат),
      `requires-python = ">=3.12"`, ruff `target-version = py312`, CI-python 3.9 → **3.13**
      (як на Pi). Додано явну залежність **`requests`** — `app/weather.py` імпортує її
      напряму, а прилітала вона транзитивно через garth (без цього фікса `pip install`
      без garth ламав імпорт бота). `curl_cffi` 0.15.0 має
      `cp310-abi3-manylinux2014_aarch64` — на Pi ставиться колесом, компіляції нема.
- [x] **Провайдер**: додати `_UserGConnProvider` у `app/garmin/providers.py` —
      аналог `_UserGarthProvider`: ізольований стан на юзера, `connectapi(path,
      **kwargs)` того самого інтерфейсу (`client.py` НЕ чіпається), resume зі
      збереженого в БД токен-блоба, `new_token` після свіжого логіну.
      `build_user_provider` перемикається на нього.
      → Зроблено; `GARMIN_PROVIDER` дефолт `garth` → **`gconn`**, `build_user_provider`/
      `_default_provider` віддають нативні класи, `garth` лишається як явний відкат.
      `client.py` справді не змінювався (крім коментарів) — **один** виняток, який
      довелось закрити в провайдері: у garth дієслово їхало кваргом
      (`connectapi(path, method="POST", json=…)`), а нативний `connectapi` — GET-only і
      передав би `method=` далі в `requests` дублем-аргументом (TypeError). Тому
      `_gconn_connectapi` мапить не-GET на `post`/`put`/`delete` (`api=True` → розпарсений
      JSON, 204 → `{}`) — інакше **тихо ламався б увесь write-шлях** (`create_workout`/
      `schedule_workout`/`delete_workout` → `push-plan`, `plan_sync`). Профілю-кешу в
      клієнті 0.3.x нема, тож `username`/`display_name` — один лінивий фетч
      `/userprofile-service/socialProfile` на інстанс провайдера.
- [x] **Формат токена**: звірити 0.3.6 token-store (`api.client.dump`/`load`,
      garth-стиль — прогін 2 OPS-01) зі збереженими в БД garth-блобами. Якщо не
      бінарно-сумісні — написати одноразову конвертацію АБО стратегію
      «стара сесія не резюмиться → тихий свіжий логін» (OAuth1 юзера 1 живий до
      ≈2027-07, тож re-login один раз не критичний).
      → **Не сумісні, і конвертувати нема чого**: нативний `Client.dumps()` — це
      простий JSON `{di_token, di_refresh_token, di_client_id}` (DI-Bearer), а garth-блоб —
      base64 `[oauth1, oauth2]`; спільного токен-матеріалу нема (звірено по коду
      `garminconnect/client.py` 0.3.7 — «garth-стиль» у прогоні 2 стосувався *каталогу*
      `dump`/`load`, не формату). Обрано другу стратегію: `providers.is_gconn_token`
      локально (json.loads, нуль мережі) відрізняє формати, garth-блоб → **один тихий
      свіжий логін** на збережених кредах, лог рівня INFO (а не страшний
      `resume failed` WARNING — це не збій резюму, це очікувана міграція).
- [x] **MFA-міст** (`app/garmin/mfa.py`): у `_run`-потоці замінити
      `client.login(email, password, prompt_mfa=...)` на конструктор/`login()`
      0.3.6 з тим самим parked-callback `prompt_mfa`. Веб-флоу `/settings`,
      `MFARequired`, 409-handler і морнінг-джоба — **без змін**. (Якщо 0.3.6 дає
      `return_on_mfa`/`resume_login` — міст можна спростити без фонового потоку;
      але це окремий крок, спершу мінімальний діф.)
      → **Коду міняти не довелось узагалі**: нативний `Client.login(email, password,
      prompt_mfa=…)` + `dumps()` — та сама сигнатура, що в garth, а міст більше нічого від
      клієнта не використовує (оновлено лише докстрінги). `return_on_mfa`/`resume_login`
      у 0.3.7 **є** — спрощення моста (без фонового потоку) свідомо лишено окремим
      кроком, щоб відкат міняв тільки провайдера.
- [x] **Token refresh**: перевірити автооновлення DI-токенів новою бібліотекою —
      «раз на рік логін» може зникнути. Якщо оновлений стан треба реперсистити —
      розширити `runtime.user_runtime` (він уже вміє зберігати `new_token`).
      → Підтверджено по коду: `Client._run_request` перед запитом кличе
      `_refresh_session` → `_refresh_di_token`, який **оновлює токени в пам'яті** (і Garmin
      може ротувати сам refresh-токен). Тобто сесія змінюється *без* логіну. Тому
      `_UserGConnProvider.new_token` — **property**, що порівнює поточний `dumps()` зі
      завантаженим блобом: `user_runtime` персистить оновлення так само, як свіжий логін,
      нових гачків не треба. (Дисковий автодамп клієнта не вмикається — ми віддаємо
      `loads()`, а не `load(path)`, тож токен нікуди, крім БД, не пишеться.)
- [ ] **Write-раундтріп** (`--write-test`, свідомо відкладений в OPS-01): один раз
      прогнати `scripts/ops01_recon_gconn.py --write-test` на Pi — create →
      schedule → delete workout — перед свапом провайдера. `push-plan` / `plan_sync`
      пишуть у календар, тож цю гілку треба закрити до релізу.
      → **Лишається живим кроком** (потрібен реальний акаунт + IP Pi). Код-сторону
      закрито: саме заради цієї гілки в провайдері з'явився метод-мапінг (див. вище),
      і він покритий тестом; але підтвердити, що Garmin приймає POST/DELETE від нового
      движка, можна лише живим прогоном. **Порядок: спершу `--write-test`, потім
      деплой** (відкат — один `pip install -e ".[garth]"` + `GARMIN_PROVIDER=garth`).
- [x] **Rate limit (PERF-05)**: підтвердити, що `client._RateLimiter` + 429-backoff
      у `client._api` працюють над новим движком (curl_cffi) без змін — після
      Cloudflare-ери агресивні патерни → ризик бана акаунта, не лише 429.
      → Лімітер живе **над** провайдером (`_api` → `get_provider().connectapi`), тож
      движок для нього байдужий. Розпізнавання 429 звірено з новою бібліотекою:
      `.error.response`-гілка (garth) не спрацює, але нативний
      `GarminConnectConnectionError("API Error 429 - …")` ловиться рядковим фолбеком, який
      у `_is_rate_limited`/`_classify_error` уже був. Змін коду не потрібно — лише
      коментарі, щоб наступний читач не «полагодив» фолбек.
- [x] **`_GConnProvider` (legacy)**: або видалити старий untested клас, або
      переписати під 0.3.6 API (у 0.2.x токени/профіль жили на `api.garth`, у 0.3.6
      немає — `AttributeError` з прогону 1). Не лишати мертвий клас, що бреше.
      → Переписано на нативний `Client` (спільна база `_GConnBase` з per-user
      провайдером), токени — у власний каталог `~/.garminconnect` (не в `~/.garth`:
      формати різні, і затирати garth-дамп означало б підпиляти відкат).
- [x] **Верифікація**: `pytest` зелений (провайдер мокається — тести не залежать
      від бібліотеки) + `ruff` + один живий цикл на Pi: `/report` → morning job →
      `push-plan --dry-run` → реальний MFA-конект через `/settings`.
      → `pytest` **925 passed, 3 skipped**, `ruff check .` чисто. Тести провайдера
      переписано на нативний движок (`tests/test_user_runtime.py`: resume, свіжий логін,
      legacy-garth-блоб, ре-персист після refresh, мапінг write-методів, лінивий профіль),
      старі garth-тести винесено в `tests/test_garth_provider_rollback.py` — вони
      **самоскіпаються**, коли extra `garth` не встановлено, і перевіряють саме те, що
      важливо в момент відкату. `tests/test_token_info.py` покриває обидва формати блоба.
      **Живий цикл на Pi — лишається** (див. нижче).

## Що лишилось (1): CI-джоба на 3.13 — ручна однорядкова правка

`.github/workflows/ci.yml` **не** входить у цей коміт: пуш з робочої гілки не має
`workflow`-скоупу (GitHub відбиває пуш, який змінює workflow-файл). Правка одна і
обовʼязкова — інакше CI на 3.9 не поставить `garminconnect` і впаде на `pip install`:

```yaml
      - uses: actions/setup-python@v5
        with:
          python-version: "3.13"  # matches the Raspberry Pi deployment target (3.13.5)
```

(було `"3.9"  # matches the Raspberry Pi deployment target`)

## Що лишилось (2): живі кроки на Pi, потрібен реальний акаунт

Код-міграцію зроблено й провалідовано мок-сьютом; нижче — те, що за визначенням не
перевіряється без живого Garmin. Порядок важливий:

1. **`scripts/ops01_recon_gconn.py --write-test`** на Pi (у тимчасовому venv) — create →
   schedule → delete workout. Єдина гілка, якої розвідка OPS-01 не торкалась.
2. **Оновити прод**: `git pull`; якщо venv на Pi зібраний старішим за 3.12 python-ом —
   **перестворити** його (`python3 -m venv venv`, `./venv/bin/python -m pip install -e ".[dev]"`),
   інакше просто переставити залежності. Перевірити, що `curl_cffi` став **колесом**
   (`pip install` не має нічого компілювати).
3. **Живий цикл**: реальний MFA-конект через `/settings` (тільки веб-процес доходить до
   MFA-гейту) → `/report` → ранкова джоба → `push-plan --dry-run`. Перший запит кожного
   юзера зробить один тихий свіжий логін (garth-блоб не резюмиться — це очікувано).
   ⚠️ `/report` і morning — це **реальний виклик Claude** (CLAUDE.md §Cost safety):
   запускати свідомо, не «на автоматі».
4. **Поспостерігати цикл**: `grep "GARMIN AUTH FAIL" bot.log`, `app.cli token-expiry`
   (має показати `[gconn]` для перелогінених юзерів), банер помилок Garmin на
   `/dashboard` (OPS-05). Не викидати garth-відкат, поки цикл не відпрацював.

**Відкат** (у будь-який момент): `pip install -e ".[garth]"` + `GARMIN_PROVIDER=garth` +
рестарт. Старі garth-блоби в БД нікуди не поділись — вони резюмляться як раніше, бо
`_UserGarthProvider` лишився незміненим; новий `gconn`-блоб просто ігнорується garth-ом
(і навпаки), тож перемикання туди-сюди коштує один свіжий логін на юзера.

## Ризики / підводні камені

- Обхід Cloudflare — гонка озброєнь: 0.3.6 теж може зламатися. Прийнято свідомо
  (постійний податок неофіційного API, ANALYSIS.md §2.4).
- **Відкат**: пін `garth==0.4.47` лишається в git-історії — стан «до» за один
  `pip install -e .`. Не видаляти робочий garth-шлях, поки нове не відкатано в
  проді хоча б цикл.
- MFA-конект досяжний **тільки у веб-процесі** (`app.garmin.mfa`) — тестувати
  через реальний `/settings`, не з CLI.
- **Cost-safety**: живий цикл `/report`/morning робить справжній Claude-виклик —
  запускати лише з дозволу (CLAUDE.md §Cost safety), решту ганяти на мок-suite.
