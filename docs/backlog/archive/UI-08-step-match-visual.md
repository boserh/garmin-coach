# UI-08 · План проти факту по кроках — візуально, а не рядком «🎯 7/8 у цілі»

**Тип:** сторі покращення (UI-аудит 2026-08-06) · **Оцінка:** M ·
**Пріоритет:** 🟡 medium · **Поверхня:** веб · **Залежності:** NF-14 ✅
(`app/stepmatch.py`), EP-01 ✅ (матчинг план/факт)

## Проблема

NF-14 порівнює **кожен робочий крок** структурного тренування з фактичним колом і знає
про кожен, влучив він у цільовий діапазон темпу чи ні (`stepmatch.match`,
`app/stepmatch.py:96-112`). Але з усього цього назовні йде:

- рядок `🎯 7/8 у цілі` (`badge`, `app/stepmatch.py:119-123`), який рендериться як
  звичайна нотатка (`app/templates/activity.html:76`);
- у збереженому JSON — `{"steps_hit", "steps_total", "misses": [...]}`: **влучення
  зберігаються лише лічильником**, попадання по конкретних кроках викидається
  (`app/stepmatch.py:116`).

Наслідок: користувач бачить «7/8», але не бачить **який саме** інтервал провалено, наскільки
і в який бік. Для інтервальної сесії це і є вся інформація: 8×400 із просадкою на останніх
двох — це одна історія (недобрана витривалість), а рівний недобір на всіх восьми — зовсім
інша (не той цільовий темп у плані). Зараз вони виглядають однаково.

Це ще й єдиний блок у застосунку, де дані про виконання є, а візуалізації нема, — при тому
що поруч уже малюються криві темпу й пульсу з тієї самої активності.

## User story

Як користувач після інтервальної сесії я хочу побачити кожен відрізок окремо: план проти
факту, наскільки повз і в який бік — щоб знати, чи це я не втягнув, чи план був не за
поточною формою.

## Обсяг

**Входить:**

1. **Зберігати посегментний результат** — `match` повертає ще й
   `steps: [{step, kind, planned, actual, hit, delta_s}]`. Формат `ActivityRecord.step_match`
   змінюється **аддитивно**: старі рядки без `steps` читаються як раніше (є лише бейдж),
   нові дають повну картину. Жодної міграції даних — минулі активності добираються
   ресинком за бажанням.
2. **Смуга кроків на сторінці активності** — по одному ряду на робочий крок: назва
   («інтервал 3/8»), плановий діапазон, факт, і горизонтальний маркер відхилення
   (влучив — зелена зона `--easy`, повз — `--intervals`/`--tempo` за величиною). Ті самі
   токени кольорів, що для типів тренувань.
3. **Підсвітка на кривій темпу** — інтервали затінюються на наявному графіку темпу
   (`charts.run_charts` уже віддає серію), щоб «7/8» читалось прямо на кривій.
4. **Агрегат у програмі** — `stepmatch.aggregate` (уже написаний і теж ніде не показаний)
   як рядок на `/plan`: «за 4 структурні сесії: 78% кроків у цілі».

**Не входить:** редагування цілей заднім числом, автозміна плану за промахами (це EP-02 і
воно вже має свій шлях), матчинг по пульсових кроках без темпу (модуль свідомо їх пропускає
— обґрунтовано в докстрінгу, не чіпаємо).

## Acceptance criteria

- [ ] Старий `step_match` без ключа `steps` рендериться як зараз (бейдж) і **не падає** —
      тест на збереженому старому JSON.
- [ ] Кількість зелених рядів у новій смузі дорівнює `steps_hit`, червоних — рядкам
      `misses` (тест на узгодженість зі старими полями: вони лишаються джерелом правди
      для лічильників).
- [ ] Сесія, де кіл менше за кроки (зупинився раніше), показує «не виконано» без факту,
      а не 0:00 — модуль уже трактує це як чесний промах, UI має не збрехати.
- [ ] Вільний біг без структури → блок не показується взагалі (`match` → `None`).
- [ ] 0 викликів Claude, 0 запитів до Garmin на рендер.
- [ ] Мобільна розкладка 320px: смуга кроків скролиться всередині своєї картки, сторінка
      не отримує горизонтального скролу (guard).

## Ризики

- Зміна формату збереженого JSON — тому строго аддитивно, зі старим шляхом читання в AC.
- Порядок «крок ↔ коло» тримається на припущенні збігу послідовностей (є в докстрінгу
  `flatten_steps`); візуалізація зробить будь-який зсув **дуже помітним** — це радше плюс,
  але треба бути готовим побачити реальні розбіжності на живих даних.
