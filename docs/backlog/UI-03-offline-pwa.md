# UI-03 · Дописати PWA: service worker, офлайн-дашборд, встановлення на екран

**Тип:** нова фіча (UI-аудит 2026-08-06) · **Оцінка:** M ·
**Пріоритет:** 🟠 high · **Поверхня:** веб · **Залежності:** UI-02 (спільний `<head>`)

## Проблема

PWA зроблена наполовину: `app/static/manifest.json` є (`display: standalone`,
`start_url: /dashboard`, теми, іконка), шаблони його підключають — але **service worker'а
немає взагалі** (`grep serviceWorker app/` → нічого). Наслідки:

- застосунок не встановлюється як повноцінний PWA (Chrome вимагає SW для install-промпту)
  — «додати на екран» дає закладку, не застосунок;
- **офлайн — біла сторінка**. Сервер живе на Pi у домашній мережі: щойно телефон вийшов з
  дому або Pi перезавантажується, недоступно навіть те, що не змінюється — сьогоднішній
  план, останній звіт, вчорашні метрики;
- кожен перехід між сторінками — повний round-trip до Pi по Wi-Fi, хоча CSS/JS/іконки
  незмінні.

Іронія в тому, що дані для офлайну **вже локальні за архітектурою** (БД як кеш, минулі дні
іммутабельні) — бракує тільки шару на клієнті.

## User story

Як користувач я хочу відкрити застосунок з іконки на телефоні поза домом і побачити
сьогоднішній план і останню готовність — навіть коли Pi недосяжний, з чесною позначкою
«дані на HH:MM».

## Обсяг

**Входить:**

1. **`app/static/sw.js`** з трьома стратегіями:
   - *cache-first* для статики (`app.css`, `app.js`, шрифти, іконки) — ключ уже містить
     `?v=` з UI-02, тож інвалідація безкоштовна;
   - *stale-while-revalidate* для `GET /dashboard` і `GET /plan` — миттєвий рендер
     збереженої копії + фонове оновлення;
   - *network-only* для всього іншого, **явним білим списком навпаки**: `/login`,
     `/register`, `/settings`, `/admin/*`, `/me/export`, будь-який `POST` — ніколи не
     кешуються.
2. **Банер «офлайн, дані від HH:MM»** — рендериться з кешованої відповіді, не приховує
   застарілість (у застосунку про готовність застаріле число гірше за відсутнє).
3. **Офлайн-фолбек `/offline`** — статична сторінка для сторінок, яких немає в кеші.
4. **Маніфест до install-критеріїв** — PNG-іконки 192/512 + `maskable` поруч із наявним
   SVG, `id`, скріншот; кнопка «Встановити» через `beforeinstallprompt` на `/info`.
5. **Розлогінення чистить кеш** — `POST /logout` шле повідомлення SW на `caches.delete()`
   (інакше персональні сторінки лишаються на пристрої після виходу).

**Не входить:** офлайн-запис (черга дій на потім), push-повідомлення (для нагадувань уже
є Telegram — дублювати канал не треба), фоновий синк.

## Acceptance criteria

- [ ] Lighthouse PWA installable → зелений; на Android з'являється справжній
      install-промпт.
- [ ] У Playwright з `context.set_offline(True)`: `/dashboard` після одного онлайн-візиту
      рендериться, показує банер офлайну з часом даних; сторінка, якої не було в кеші, дає
      `/offline`, а не браузерну помилку.
- [ ] `/settings` **ніколи** не потрапляє в кеш (перевірка вмісту `caches.keys()` після
      візиту) — там ключі й креденшели.
- [ ] Після `POST /logout` кеш порожній (той самий тест).
- [ ] Оновлений `app.css` підхоплюється без ручного «очистити дані сайту» (`skipWaiting` +
      `clients.claim` та новий `?v=`).
- [ ] Вимкнений/непідтримуваний SW не змінює нічого — сторінки працюють як зараз.

## Ризики

- **Кешований персональний контент на пристрої** — головний ризик фічі; закривається
  списком «ніколи не кешувати» + чисткою на `/logout`, обидва в AC.
- Застарілі дані, показані як свіжі — тому банер із часом обов'язковий, а не опційний.
- «Залипший» SW при помилковому релізі — тримати `sw.js` крихітним і без залежностей,
  версію брати з того самого `asset_v`.
