# NF-25 · Динаміка бігу: каденс, контакт із землею, дрейф форми на втомі

**Тип:** нова фіча (аудит коду 2026-08-05, кат. C) · **Оцінка:** M ·
**Пріоритет:** 🟠 high · **Поверхня:** `/activity` + звіт + травматичний радар ·
**Залежності:** NF-04 ✅ (injury radar), EP-15 ✅ (series-інфраструктура), EP-12 ✅ (болі)

## Проблема

`fetch_activity_series` тягне рівно чотири канали: `d`, `p`, `hr`, `e`. Каденс,
час контакту з землею, вертикальні коливання і довжина кроку — **не запитуються взагалі**
(grep: `cadence`/`groundContact`/`verticalOscillation`/`strideLength` відсутні в
`app/garmin/`). Це найпряміший наявний сигнал біомеханіки, і саме він передбачає травму
краще за обсяг: каденс, що падає на 20-й хвилині довгого бігу, — це втома стабілізаторів,
а не «легкий день».

NF-04 сьогодні працює на обсязі, ACWR і суб'єктивному болю — тобто ловить перетрен, але
не ловить **форму**, яка сиплеться в межах однієї сесії.

## User story

Як бігун я хочу знати, чи тримаю каденс до кінця довгого бігу і чи не збільшується час
контакту із землею з тижнями — щоб побачити накопичену втому до того, як заболить.

## Обсяг

**Входить:**

1. **Розширення series** — додати канали `cad` (кроків/хв), `gct` (мс), `vo` (см) до
   `_SERIES_METRIC_KEYS["running"]`; **бамп ключа кеша на `series:v3:<id>`** (v2 без
   нових каналів лишається валідним для старих записів — не переписуємо історію).
   Довжина кроку рахується (швидкість/каденс), не тягнеться окремо.
2. **Чистий модуль `app/rundynamics.py`:**
   - **дрейф каденсу в межах сесії** — Δ між першою і останньою третиною бігу (тільки
     рівні відрізки за `e`, інакше підйом дасть хибний дрейф);
   - **тренд по тижнях** — медіанний каденс/GCT на легких бігах у порівнянному коридорі
     темпу (реюз `app/efficiency.py::_easy_corridor` — та сама проблема нормалізації);
   - **асиметрія** — якщо DTO віддає баланс (не всі годинники), інакше секція мовчить.
3. **Споживачі:** рядок у `/activity`-аналізі (факт + чи є дрейф), сигнал у `app/injury.py`
   (дрейф каденсу > порогу N сесій поспіль → +ваг у ризик), плитка тренду на детальній
   сторінці активності (наявний `app/charts.py::run_charts` — ще одна серія).

**Не входить:** поради з техніки бігу («приземляйся на середину стопи») — це те, за що
користувачі ненавидять конкурентів (ANALYSIS §2.2); ми повідомляємо факт і зміну, не
даємо біомеханічних приписів.

## Acceptance criteria

- [ ] Годинник без accessory/HRM-Pro → канали `None`, модуль повертає `None`, усі
      споживачі мовчать (найчастіший реальний кейс — не помилка).
- [ ] Дрейф каденсу рахується лише на сесіях ≥ 30 хв і на відрізках без набору висоти
      (тест на синтетичному профілі «рівний → підйом»).
- [ ] Тренд по тижнях не змішує темпові й легкі біги (коридор темпу обов'язковий).
- [ ] `series:v2` записи читаються без міграції даних; бекфіл — опційний
      `app.cli backfill-series --force` (наявна команда, лише прапорець).
- [ ] Новий контекст — у ключ дедуп-кеша.
- [ ] Тести: `tests/test_rundynamics.py` + парс нових колонок у `test_activity_series.py`.

## Вартість LLM / запити до Garmin

LLM: 0 нових викликів. Garmin: 0 нових запитів (ті самі `/details`, більше колонок).
Диск-кеш: +~15% розміру series-файлів.

## Ризики

- Ключі метрик у `metricDescriptors` відрізняються між моделями годинників → шукати за
  ключем із фолбеком `None`, ніколи за індексом (уже так у коді).
- Бамп до `v3` знецінює наявний диск-кеш для нових фетчів → одноразовий повторний фетч
  лише для активностей, які реально відкриють; історія не перетягується масово.
